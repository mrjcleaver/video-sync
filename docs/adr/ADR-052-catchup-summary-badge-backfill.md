# ADR-052: Catch-Up Summary Badge Backfill

**Status**: Proposed
**Date**: 2026-06-08
**Deciders**: Architecture Team
**Related**: ADR-046 (prompt-driven summaries on Drive), ADR-047 (automated catch-up), ADR-049/050 (provenance graph used by the future ADR-053)

---

## Context

ADR-046 introduced the summary badge — `📄 M:NN L:NN T:NN C:NN` rendered by `SummaryLozenge` on every video card. The badge is populated when a record has the `{summary_doc_id, summary_prompt_version, summary_counts}` triple. Until then it shows `📄 —`.

Summaries are generated by `/api/summary/generate`, invoked today from two places:

1. **Per-record "Summarise" button** on a `VideoCard` — operator clicks one record at a time.
2. **`runCatchUp` orchestrator** (ADR-047) — runs a per-record pipeline `hydrate_transcript → link_siblings → ensure_summary`. The summary stage (`tryEnsureSummary`, `catchupOrchestrator.ts:307`) skips records with `transcript_text < 200 chars`, returning `reason: "no transcript"`.

Operator's observation:

> "Catch up needs to be able to backfill the Summary prompt badges for any video in the catalogue."

The `runCatchUp` pipeline does the right per-record work but couples summarisation with transcript hydration, sibling matching, and a cost-cap-aware filter (`isPublishable`). It's hard to run *only the summary stage* against the whole catalogue without dragging the rest of the pipeline along. The operator wants a dedicated button: walk every record, generate or refresh the badge.

There's an orthogonal class of records — those without transcripts — where the right behaviour is to first **find a transcript** from a related record via the provenance graph (e.g. a Zoom record's transcript can come from the paired Fireflies via `TranscribedFrom`). That's substantial work in its own right and is **out of scope for this ADR**; tracked separately under [the proposed ADR-053 — Transcript Provenance Lookup](#references).

## Decision

Add a **Summary Badge Backfill** card to the Catch-Up panel, alongside the existing broadcast-pair migration (ADR-049 slice 5) and YouTube row backfill (ADR-049/050 C1-A) cards. Structurally parallel to those: a pure scanner (`findRecordsNeedingSummaryBadge`) + a sequential driver (`runSummaryBadgeBackfill`) + a UI card in `CatchUpPanel.tsx`.

### Scope — transcript-having records only

Only records where `transcript_text.length >= 200` are eligible work items. Records with no transcript stay out of this backfill; the "📄 —" empty state remains. ADR-053 will cover the path of finding transcripts via provenance.

### Three outcomes the scanner distinguishes

| Reason | Condition | Action |
|---|---|---|
| **`missing`** | `!summary_doc_id` | Generate summary, populate badge fields. |
| **`stale`** | `summary_doc_id && summary_prompt_version < currentPromptVersion` | Re-generate against current prompt. |
| **(skip)** | `summary_doc_id && summary_prompt_version === currentPromptVersion` | No work. |

### Lock handling

The default backfill **skips** records with `summary_locked === true`. Locked records represent operator-curated content — operator deliberately ran `lock_summary` to freeze a particular version. The backfill UI exposes an explicit checkbox `[ ] Include locked records (override)` so an operator can intentionally override; that path is one-click and visible, not silent.

This is symmetric to how `tryEnsureSummary` already treats locked records (`catchupOrchestrator.ts:309` — `if (record.summary_locked) return { generated: false, reason: "locked" };`).

### One button, handles all eligible cases

Per operator preference: a single Run Backfill button handles missing + stale + (optionally) locked-with-override in one pass. The work-list count surfaces the pre-flight, e.g. `Run backfill (12 missing, 4 stale)`. The summary line distinguishes outcomes: `generated`, `skipped_locked`, `skipped_no_transcript`, `errors`.

### Cost guard

Summary generation hits the LLM (default model is google/gemini-2.5-pro per the existing flow, ~$0.001–$0.005 per record depending on transcript length). The backfill driver respects a per-run cost cap parameter, defaulting to **$5.00 USD**. Cost estimation reuses `estimatePerRecordCost` from `llmCost.ts`. When the cap would be exceeded, the driver emits a `stopped_cost_cap` outcome and halts; the operator can re-run to continue.

### Per-record idempotency

`tryEnsureSummary`'s existing checks (`current → skip`, `locked → skip`) make per-record idempotent semantics free. The new backfill driver reuses `tryEnsureSummary` directly rather than reimplementing the generate logic. Difference vs. existing catch-up: the new driver doesn't invoke `hydrate_transcript` or `link_siblings`; it only invokes `tryEnsureSummary`.

## Implementation sketch

Pattern mirrors `youtubeIngest.ts` (C1-A backfill):

```ts
// web/src/lib/summaryBadgeBackfill.ts (new)

export interface MissingSummaryBadge {
  record: VideoRecordJSON;
  reason: "missing" | "stale";
}

/** Pure scanner — no I/O, easily unit-testable. */
export function findRecordsNeedingSummaryBadge(
  allRecords: VideoRecordJSON[],
  currentPromptVersion: number | null,
  opts?: { includeLocked?: boolean },
): MissingSummaryBadge[] { ... }

export type SummaryBackfillProgressEvent =
  | { type: "started"; total: number }
  | { type: "item_done"; index: number; total: number; recordTitle: string;
      outcome: { kind: "generated"; recordId: string }
             | { kind: "skipped_locked" }
             | { kind: "skipped_current" }
             | { kind: "stopped_cost_cap"; spent: number; cap: number }
             | { kind: "error"; error: string } }
  | { type: "complete"; total: number;
      totals: { generated: number; skipped: number; errors: number; cost_spent_usd: number } };

export async function runSummaryBadgeBackfill(
  onEvent: (ev: SummaryBackfillProgressEvent) => void,
  log?: (msg: string, ctx?: Record<string, unknown>) => void,
  opts?: { includeLocked?: boolean; costCapUsd?: number; actor?: Actor | null },
): Promise<...>;
```

CatchUpPanel adds a third card (parallel to the green YouTube row backfill + purple broadcast-pair migration). New colour family (blue: `rgba(96, 165, 250, …)`) so the three operator-invoked maintenance actions are visually distinct.

## Consequences

**Positive**
- One operator action clears the summary-badge debt across the whole catalogue without triggering the rest of the catch-up pipeline (no spurious sibling links, no transcript-hydration attempts).
- Stale badges (when the prompt version is bumped via Connections → Prompt → save) become trivial to refresh — operator runs the backfill once.
- Lock-override option lets an operator decisively re-summarise without manually unlocking records first.

**Negative / careful**
- The backfill *will* hit the LLM N times for N missing/stale badges; the cost cap is the safety. Operator should glance at the pre-flight count before clicking.
- A prompt-version bump effectively invalidates every existing badge. The first backfill after a bump is the most expensive. Acceptable: operator bumps the prompt deliberately, knowing they're committing to a regen pass.
- Records without transcripts stay at `📄 —` until ADR-053 lands. The badge isn't "wrong" — it's accurate — just less satisfying than fully populated. Documented as the explicit out-of-scope.

**Risks**
- Concurrent invocations (operator clicks twice quickly) would race the same `tryEnsureSummary` calls. Mitigated by the existing `videoStore.mutate` locking semantics + the `summary_prompt_version === currentPromptVersion` check inside `tryEnsureSummary` — second run sees the first run's result and skips.

## Alternatives considered

| Option | Why rejected |
|---|---|
| **Fold into existing Run Catch-Up** by changing `tryEnsureSummary` to not return early on missing transcript | Mixes the no-transcript concern in. The operator-paired ADR-053 specifically pulls that into its own scope. Keeping ADR-052 narrow lets ADR-053 be designed cleanly. |
| **Auto-run the backfill on every prompt-version bump** | Removes operator agency over when the cost is incurred. The cost cap mitigates somewhat but operator-invoked is the explicit pattern. |
| **Walk records server-side via a background job** | Would need a separate Cloud Run job + persistent state. Existing client-driven model is simpler and the cap keeps runtime bounded. Worth revisiting if operator catalogues grow beyond ~1k records. |
| **Generate badges with no doc_id (metadata-only stub)** | The badge UI in `SummaryLozenge.tsx:58` short-circuits on `!docId || !counts` showing the empty state. Stub-only metadata would either need new UI states or end up indistinguishable from the empty state today. Not useful. |

## Open Questions

1. **Cost cap default**: $5.00 picked from gut. At ~$0.003 per record × 100 records that's $0.30 — well under cap. The cap is more for guarding against an operator running it against 10k+ records or repeatedly. Tunable, easy to adjust.
2. **Should "include locked" force-regen lock state?** Today: operator manually re-locks after the regen. ADR-052 doesn't auto-relock, since the relock command is per-record and we'd be guessing about intent. Worth a follow-up if the manual relock is painful in practice.
3. **Hooking into prompt version changes**: should the Catch-Up panel surface "There are 47 stale badges" on the new card based on a live count, even when the operator isn't actively looking? Cheap to compute via the scanner; non-breaking to add.
