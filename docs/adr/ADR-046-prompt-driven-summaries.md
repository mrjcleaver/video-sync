# ADR-046: Prompt-Driven Video Summaries on Drive

**Status**: Proposed
**Date**: 2026-05-27
**Deciders**: Architecture Team
**Related**: ADR-022 (YouTube description provenance footer), ADR-024 (post-processing webhook & email), ADR-029 (auto-Shorts generation), ADR-031 (server-side rule persistence), ADR-035 (persistence topology), ADR-039 (Drive-based artifact storage), ADR-041 (app-level audit log)

---

## Context

Operators run 2–3 hour Friday Hackerspace-style sessions with extensive live chat. Today the catalog stores transcripts on Drive (ADR-039) and embedded Zoom chat as a separate Drive artifact (ADR-039 slice 3). Neither artifact is digestible at length:

- A 100K-token transcript is unreadable end-to-end.
- The chat is timestamped but disconnected from the transcript's narrative.
- Operators need to surface what's actually valuable in a 3-hour recording — key moments, learnings, takeaways, and the discussions where the audience reacted most strongly.

There's also a **consistency** concern. Every operator currently runs their own ad-hoc Gemini/Claude prompt in a separate window, paste-extracting chapters. Output varies wildly per operator and per session, and refining "what makes a good summary for our content" means redoing every prior session by hand. The org needs *one* prompt, versioned, that produces *one* summary shape, with a one-click path to regenerate the back catalog when the prompt improves.

## Decision

Introduce a **prompt-driven summary artifact** stored as a native Google Doc alongside the transcript on the Workspace Shared Drive. The summary's authoring prompt is a versioned, org-shared resource. A prompt version bump offers to regenerate every *unlocked* summary in bulk. Counts of the four section types surface in the Overview as `M:NN L:NN T:NN C:NN` and link to the Doc.

### What the summary contains

A chapter-oriented breakdown of the video, derived from the transcript + embedded chat. Four structured sections per chapter:

| Section | Indicator | Meaning |
|---|---|---|
| **Key Moments** | `M` | Narrative beats in the video itself — concept introductions, decisions, demos, transitions |
| **Key Learnings** | `L` | Generalisable insights — things a viewer would write down |
| **Key Takeaways** | `T` | Action items — what to do next |
| **Chat-Sparked Discussions** | `C` | Moments where the embedded chat showed concentrated engagement; the entry records *what was said in the video* that triggered the chat, with quotes from the chat itself |

Each section is a bulleted list with a timestamp + a one-paragraph summary referencing the speaker(s) and (for `C`) the chat author(s).

### Storage: native Google Doc on Drive

Adds a new artifact kind `summary` to ADR-039's layout:

```
{Channel}/{YYYY-MM}/{recordId}/summary.gdoc
```

Created via Drive's MIME conversion (`application/vnd.google-apps.document`), not markdown, so operators can edit, comment, and share in Google Docs natively. The Doc carries a first-line banner:

```
🤖 Generated by video-sync summary-prompt v{N} on {ISO timestamp}.
   Edit freely. Lock the record to preserve this summary from prompt-bump regenerations.
```

The prompt version + generation timestamp are also stored in the file's `appProperties` (machine-readable, doesn't depend on the operator preserving the banner). That's how the bulk-regen job decides whether a Doc was written by the current prompt version.

### The prompt: org-shared, versioned

Lives at `data/summary-prompt.json` on the FUSE bucket (server-authoritative per ADR-035 L2):

```json
{
  "current": {
    "version": 3,
    "text": "You are a video summariser... <prompt body> ...",
    "model": "anthropic/claude-opus-4.7",
    "updated_at": "2026-05-27T15:00:00Z",
    "updated_by": "martin.cleaver@agentics.org"
  },
  "history": [
    { "version": 2, "text": "...", "model": "...", "updated_at": "...", "updated_by": "..." },
    { "version": 1, "...": "..." }
  ]
}
```

Versions are monotonic. History retains every superseded prompt so a regeneration audit can answer "which prompt wrote this doc?" even years later. Admin role required to edit (ADR-036 / ADR-041 — write is `audit: mutation`).

### Lock semantics

Each `VideoRecord` gains `summary_locked: bool`. When an operator hand-edits a generated summary in Docs and wants to preserve it across prompt-bump regenerations, they toggle **Lock** on the card. The bulk-regen flow skips locked records. Locking is reversible.

The Drive Doc itself isn't locked at the Drive level — operators can always edit it. The lock is a regen-skip signal living on the catalog record.

### Bulk regeneration

Editing the prompt and saving offers an immediate **"Regenerate {N} unlocked summaries? — est. ${cost}"** action, where `N` is the count of unlocked records with a non-empty transcript and the cost estimate is `Σ(transcript_tokens) × model_rate`. The regen job:

1. Iterates the catalog by `recorded_at desc` (recent first — operators care about recent ones).
2. For each unlocked record with a transcript: fetches transcript + chat from Drive, invokes the LLM with the new prompt, overwrites `summary.gdoc`, updates `appProperties.prompt_version`, updates `summary_counts` on the VideoRecord.
3. Emits a `SummaryGenerated` event per record (ADR-041 audit; visible in EventLog).
4. Pauses at a configurable cost cap (default $5 per batch) and surfaces "resume / cancel" to the operator.
5. Persists job state to `data/summary-regen-state.json` so a Cloud Run cold-start can resume mid-batch.

Single-record regenerate is also available from each card — useful when the prompt is fine but one specific transcript was bad.

### Counts in the Overview

`BackfillOverview.DateList` gains a fifth lozenge per row, after the Drive lozenge:

```
[ Fri 3   ● Title here   Zoom   YT:Public   Kaltura   Drive   📄 M:8 L:5 T:3 C:2 ]
```

The lozenge is a clickable link to the summary Google Doc. Hover shows:
- The prompt version that wrote it (`Summary prompt v3 · 2026-05-27`)
- A 🔒 prefix if `summary_locked` is true
- A faded styling if the doc's `appProperties.prompt_version` is older than the current prompt (signals "regenerate available")

Counts come from `summary_counts: { M, L, T, C }` on the VideoRecord — populated when the summary is generated, by counting bullets under each section heading.

### LLM choice and long-context strategy

Default model: routed through OpenRouter to a long-context model. Configured per-org in `data/summary-prompt.json` (`model` field). The system picks a strategy by transcript token count:

- **≤ 200K tokens**: single-pass. Full transcript + chat lines inline.
- **> 200K tokens**: two-pass.
  1. Chapter detection on the transcript alone → returns chapter boundaries with timestamps.
  2. Per-chapter summarisation, fed the chapter's transcript slice + chat lines whose timestamp falls inside the chapter range.

The two-pass mode is deterministic given the same prompt + same transcript, so reproducibility holds.

## Implementation slices

| Slice | Scope |
|---|---|
| **1. Schema + Drive write** | VideoRecord gains `summary_doc_id`, `summary_prompt_version`, `summary_locked`, `summary_counts`. WASM commands `set_summary_metadata`, `lock_summary`, `unlock_summary`, plus `SummaryGenerated` / `SummaryLocked` events. Drive lib `createOrUpdateSummaryDoc(recordId, markdown, promptVersion)` using `application/vnd.google-apps.document` MIME conversion. |
| **2. Prompt + single-record generate** | `data/summary-prompt.json` resolver (server-side, 5-min cache like ADR-042 shared creds). `POST /api/summary/generate?recordId=…` route: fetch transcript + chat from Drive, build LLM payload, call OpenRouter, parse structured output, write summary Doc, update VideoRecord. UI: "Generate summary" button on cards that have a transcript. |
| **3. Counts + Overview lozenge** | Compute counts from parsed sections during generate. Render the 📄 M:N L:N T:N C:N lozenge in `BackfillOverview.DateList`. Click → open Drive Doc; hover → prompt version + lock state. Stale-prompt indicator (faded styling). |
| **4. Bulk regen on prompt bump** | Admin "Summary Prompt" panel: edit prompt, save, see "Regenerate {N} unlocked summaries — est. ${cost}" CTA. Server-side job with persistent state + cost-cap pause. SSE progress stream to the panel. |
| **5. Lock UI + audit polish** | Lock/unlock buttons on cards. EventLog entries via ADR-041. Card-detail panel shows "last regenerated: prompt v3 on …" and a 🔄 button when stale. |

Cross-cutting: a `summary_locked` migration default of `false` for existing records; no need to backfill the Drive Doc until the operator generates it.

## Consequences

**Positive**
- Operators can scan a 3-hour session in 60 seconds via the four indicator counts before deciding to open it.
- Prompt iteration becomes cheap: edit, regen, compare. The history captures what the team learned about how to summarise their content.
- The `C` (Chat-Sparked Discussions) section is novel — surfaces engagement signal that's currently lost in the gap between transcript and chat artifacts.
- The Doc is editable. When the LLM gets something wrong, the operator fixes it in Docs and locks the record. Subsequent prompt bumps don't clobber the fix.

**Negative**
- LLM cost is real. A backfill regen of 100 records × 100K-token transcripts × frontier model ≈ tens of dollars per pass. Mitigated by the per-batch cost cap, "unlocked only" scope, and a cost preview before run, but prompt churn isn't free.
- More state on `VideoRecord`. Four new fields, three new commands, two new events. Manageable but accumulates — pushes us closer to needing the ADR-035 L3 server-side aggregate.
- Drive's `application/vnd.google-apps.document` conversion isn't lossless for complex markdown (tables, nested lists deeper than 2 levels). The prompt should be tuned to produce structures Drive renders cleanly — bullets, headings, paragraphs.

**Risks**
- A prompt change with a subtle bug could trigger an expensive regen of every record. Mitigation: the CTA shows estimated cost (tokens × model rate) before running, and the cost cap halts mid-run if exceeded. Operators can also dry-run on a single record first.
- Locked summaries drift over time as the prompt improves but the lock holds. Addressed by showing prompt version in the lozenge tooltip plus a "diverged from prompt vN" indicator on the card.
- Two-pass mode may produce chapter boundaries that the per-chapter summariser can't fully reconstruct. Worth a one-time validation against a representative session before defaulting to two-pass.
- `appProperties` has a 30 KB per-file limit — fine for our needs (we'd store ~200 bytes) but worth noting against future expansion.

## Alternatives considered

| Option | Rejected reason |
|---|---|
| **Inline summary on the VideoRecord (no Drive Doc)** | Loses editability and shareability. Operators want to send a summary link to a teammate; a JSON blob in the catalog doesn't satisfy that. |
| **Per-operator prompts** | Conflicts with ADR-035's "shared by default" stance and would mean every operator's regen produces a different summary. The prompt is the team's institutional knowledge of how to summarise their content. |
| **Manual prompt-version tracking via banner text only** | Banner gets edited or stripped by Docs users. Use both: banner for humans, `appProperties` for the system. |
| **Markdown `.md` file instead of native Google Doc** | Less editable in Docs (opens as plain text). Native conversion is the friction we want to remove. |
| **Single-pass for all transcripts** | OK for < 200 K-token sessions; 3-hour streams with chat blow context budget on most non-frontier models. Two-pass keeps cost predictable. |
| **Auto-regen on prompt save (no operator confirm)** | Spending real money without an explicit click violates the ADR-022/ADR-024 "operator approves consequential actions" pattern. CTA-with-cost is the right shape. |

## Open Questions

1. **Cost cap default and unit.** $5 per batch is a guess. Should the cap be per-record (e.g. $0.50) instead of per-batch? Per-batch fits "I edited the prompt, regen everything"; per-record fits "stop me from spending $40 on one giant 5-hour session". Possibly both, with an OR-min.
2. **Cross-record chapter linking.** When a record has a `SameEvent` sibling (ADR-033: Fireflies + Zoom of the same meeting), should chapters from each capture be merged into one summary, or stay separate? This ADR proposes one summary per record. Merging is its own follow-up ADR.
3. **Stale-prompt review nudge.** Should locked summaries also stamp a "diverged from prompt vN" warning that escalates over time, prompting periodic review of old locked ones? Useful but adds UI complexity.
4. **Chat-source coverage.** Today only Zoom CHAT is captured (ADR-039 slice 3). YouTube Live chat capture is not implemented. Should the `C:NN` counter be hidden when no chat was captured, or always shown as `C:0`? Suggest: hide when `chat.md` Drive artifact is absent; show `C:0` when present but empty.
5. **What about non-English transcripts?** Should the prompt be language-aware, or does the LLM handle it? Default: trust the model, but allow a per-record language override in the regen call.
