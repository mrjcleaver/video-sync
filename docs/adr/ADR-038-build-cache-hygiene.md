# ADR-038: Build Cache Hygiene and Disk Reclamation

**Status**: Accepted
**Date**: 2026-04-22
**Deciders**: DevOps / operator

---

## Context

The devcontainer disk filled to 98% during normal development (137 MB of duplicated SWC binaries, growing `.next/` build dirs, accumulating Docker layers, Rust target trees). There was no documented place to look for what's safe to delete vs. what holds load-bearing state, and no tool to do it consistently.

This ADR catalogues the regenerable artefacts and ships a `scripts/prune-build-artifacts.sh` utility that handles them at three escalating levels.

---

## What's regenerable vs. load-bearing

### Regenerable (safe to delete)

| Path | Regenerated by | Typical size | When to keep |
|------|---------------|--------------|--------------|
| `web/.next/` | `npm run build` (~30s) | 100–300 MB | Live dev session (re-build cache) |
| `web/tsconfig.tsbuildinfo` | `tsc --build` (~5s) | <20 MB | If you want incremental TS |
| `web/node_modules/@next/swc-linux-x64-musl` | nothing — only used inside the Docker build (Alpine), which has its own `node_modules` | ~140 MB | Never on a glibc devcontainer |
| `.claude-flow/.trend-cache.json` | regenerated on the next agent run | <5 MB | Never |
| `pkg/` (built WASM) | `wasm-pack build --target web --out-dir pkg` (~15s) | <20 MB | Live dev where you use the WASM module |
| `web/node_modules/` | `npm ci` (~30s) | ~1.5 GB | Every active dev session |
| `target/` (Rust build dir) | `cargo build` / `wasm-pack build` (~5–15 min cold) | 1–3 GB | Active Rust dev |
| Docker images, builder cache | next `./deploy.sh` rebuilds | 1–5 GB | If you're about to deploy and want the cache |

### Load-bearing — DO NOT delete

| Path | Why |
|------|-----|
| `data/` | Server-side persistent state. `data/rules.json`, `data/backfill-state.json`, etc. (ADR-018, ADR-031). Even though `/app/data` is currently ephemeral on Cloud Run (no FUSE mount, ADR-018 addendum), the local copy in this directory is the operator's source of truth for processing rules and backfill quota. |
| `.git/` | Version control. |
| `web/src/`, `src/`, `docs/`, `scripts/` | Source. |
| `.env*` | Environment files (which we never commit anyway). |
| `node_modules` of local dev tools the operator depends on (gh, claude-code, etc.) | Outside the repo. |

## The `prune-build-artifacts.sh` utility

```
bash scripts/prune-build-artifacts.sh                 # dry-run, safe level
bash scripts/prune-build-artifacts.sh --apply         # actually delete (safe)
bash scripts/prune-build-artifacts.sh --apply --aggressive
bash scripts/prune-build-artifacts.sh --apply --nuclear
```

Three escalating levels:

| Level | Removes | Recovery cost |
|-------|---------|---------------|
| **safe** (default) | `web/.next/`, `web/tsconfig.tsbuildinfo`, the Alpine SWC binary, `.claude-flow/.trend-cache.json`, `pkg/` | `npm run build` (~30s); `wasm-pack build` (~15s) |
| **aggressive** | safe + `docker image prune -a` + `docker builder prune -a` | next `./deploy.sh` rebuilds the image cold (~3 min instead of ~30s) |
| **nuclear** | aggressive + `web/node_modules/`, `target/` | `npm ci` + `wasm-pack build` from scratch (~5 min) |

**Default mode is dry-run** — the script prints what it would delete without touching anything. Pass `--apply` to actually remove.

The script always prints `df` output before and after, so the operator sees how much was reclaimed.

---

## Decisions

1. **`.npmrc` with `libc=glibc`** prevents the musl SWC binary from being re-downloaded on every `npm install`. Saves the 137 MB recovery from being a recurring cost. Already landed in commit `1e4ac49`.

2. **Script lives in `scripts/`** alongside `gcs-fuse-setup.sh`, `iap-setup.sh`, `gen-adr-index.sh`. CLAUDE.md says no scripts in repo root.

3. **Script defaults to dry-run** because the difference between "delete `.next/`" and "delete `data/`" is one typo. The friction of typing `--apply` is the safety net.

4. **No automatic / scheduled invocation.** Pruning is operator-initiated. A cron-driven version is tempting but:
   - There's no good signal for "the operator is mid-build and needs the cache."
   - The aggressive/nuclear levels are too destructive to run on a timer.
   - The safe level saves <500 MB on a fresh devcontainer; not worth the coordination.

5. **Docker prune flags `-a -f`** — remove all unused images, force without prompting. The script's `--apply` gate is the single confirmation.

## Consequences

### Positive

- Clear documented separation between regenerable and load-bearing state.
- One command to reclaim disk at the level the operator wants.
- Dry-run default prevents accidents.

### Negative

- Aggressive/nuclear modes lengthen the next build by 1–5 minutes. Operator must time them around their workflow.
- The script doesn't know which build cache the user is currently using; running `--aggressive` mid-deploy could clobber a build in progress. Mitigated by dry-run default and operator judgement; not worth a process-locking design at this scale.

### Risks

- **Accidental nuclear during active dev** — the operator types `--nuclear --apply` while a build is in flight. Mitigation: the script's exit is fast and the artefacts re-create automatically; worst case is ~5 min lost.
- **`data/` deletion via shell glob** — explicitly NOT in the script's path list, but a shell glob in another context could still hit it. Mitigation: keep `data/` in `.gitignore` so a stray `git clean -fdx` doesn't take it; document the rule that scripts touching disk must enumerate paths, not glob.
